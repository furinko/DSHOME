> 评估对象：`E:\DSHOME` 仓库（DSHOME = 基于 DeepSeek Harness 的个人桌面客户端 monorepo）

> 评分口径：**整体工程成熟度综合评分**（10 分制，6 维度加权，见 §2）。如需要按其他口径（纯代码质量 / 单包 / 交付健康度）重新出分，可再行调整。

## 1. 结论

**综合得分：7.2 / 10（B+）**

对一个"给自己用 + 给别人用"的 AI 桌面客户端而言：**架构设计与文档是标杆级**（事故复盘文化尤其突出），**短板在自动化测试、CI 与发布闭环的一致性**（含一处已实测确认的 updates.json sha256 漂移）。

一句话评价：**"会把自己做的东西当成产品来经营"**——4 层 patch 架构、rationale 决策记录、事故→门禁→复盘闭环、零依赖工程细节，都达到了远超个人项目的专业度；但质量保障仍停留在"脚本冒烟 + 人工清单"，且发布流程存在一处未闭环。

## 3. 亮点（有据可查）

1. **事故复盘文化是最深的隐性资产**：ISSUE-003 完整记录了「7-Zip 坏包 → 换 Inno 仍坏 → 根因是打包器不保留 junction 语义」的定位过程，落地了 **payload 侧根治 + Inno Excludes 双重兜底 + junction 冒烟断言**，最终重建发布并线上覆盖验证。这套"事故 → 门禁 → 复盘 → 沉淀"的闭环在个人项目里非常少见。
2. **架构文档诚实且可交接**：`docs/ARCHITECTURE.md` 同时记录设计决策（rationale，"别轻易改"）和**已知债务自曝**（dshome/core 零消费者、settings.yaml 与 patch 漂移）——接手者友好，不自欺。
3. **零依赖的工程细节**：启动器/卸载器用 Windows 自带 csc 编译（DSHOME.exe 5.6KB / UninstallDSHOME.exe 4.6KB）；junction 运维纪律（删 junction 用 `Remove-Item` 勿用 `rmdir /s /q`）；依赖版本全锁定 + 全量 bump 策略；dsh-evolve vendor 化消除 GitHub 下载依赖。
4. **版本一致性管理意识**：updates.json / 品牌 DSHOME_VERSION / 依赖版本三处有明确同步清单（虽然有一处漏网，见 §4.1）。

## 4. 扣分点与发现的问题

### 4.1 🔴 仓库根 updates.json 与线上发布物不一致（实测确认）

| 位置 | sha256 | 结论 |
|---|---|---|
| 线上 v0.2.0 安装包（已发布，gh release 确认 211,399,028 字节） | `54d2c586a0f8a283678424f8ae81e8380d5396d83afa1915e4ffa71a53126777` | 正确 |
| `build-stage\payload\updates.json`（打进安装包的一份） | `54d2c586…` | 正确 |
| **仓库根 `E:\DSHOME\updates.json`** | **`a826ed34a35936b37565f5ef2bee03105c9b07a001282b082ed3fafeb0a9541d`** | **❌ 旧值，未同步** |

影响：README 写明 updater.cjs **从 GitHub raw 固定拉取仓库根 updates.json** ——若 updater 校验 sha256，0.1.x 用户升级 0.2.0 时校验失败、更新不可用；即便不校验，也违反自家发布门禁清单第 5 条（"同步 updates.json 的 version/url/sha256"）。属于**打包正确但发布清单没同步**的漏网之鱼。

### 4.2 无自动化测试 / CI

- `packages/` 下没有任何 `describe(` / `test(` 测试用例（仅正则 `.test()` 误命中）；
- 无 GitHub Actions 等 CI；打包依赖本机 ISCC（曾出现"本机未找到 ISCC"导致重建延迟）；
- 3 次事故（ISSUE-001 插件入口缺 apply、ISSUE-002 agent-teams 版本族不兼容、ISSUE-003 安装包 junction 实体化）全部靠人工踩出，缺少自动化回归防线。

### 4.3 交付历史

v0.2.0 同一版本两次发布损坏（7-Zip SFX 版 junction 实体化；Inno 版毒树残留 @aws-sdk/@earendil-works），说明此前打包流程并不可靠——现已通过 verify-payload 门禁 + smoke junction 断言 + Inno Excludes 兜底根治。

### 4.4 其他小项

- README 四包表漏了实际存在的第 5 包 `dshome-assistant-identity`（文档与代码漂移的又一例）；
- 已知债务未排期：dshome/core 扩展点零消费者、settings.yaml 管理视图与 patch 加载真相可能漂移（已见实例）。

## 5. 改进建议（按优先级）

| 优先级 | 建议 | 说明 |
|---|---|---|
| 🔴 P0 | 同步仓库根 updates.json 的 sha256 为 `54d2c586…` 并 push | 与 `build-stage\payload\updates.json` 一致；修复潜在更新校验失败 |
| 🔴 P0 | 将"根 updates.json ≡ 线上 asset sha"做成脚本断言（如 `scripts/release-check.mjs`）并入发布门禁 | 防止 §4.1 类漂移再发生；门禁清单第 5 条从"人工同步"升级为"脚本校验" |
| 🟡 P1 | 引入 GitHub Actions：跑 `syntax-check` + `smoke` + `verify-payload` | 低成本拿到持续回归防线；有条件时 CI 内装 ISCC 出包并上传 release，消除单机单点 |
| 🟡 P1 | 为核心纯函数补最小单测 | plugin-store 的 patch 解析/四级描述回退链、plugin-api 的 IP 校验、launcher --selfcheck 等优先 |
| 🟢 P2 | 排期处理已知债 | dshome/core 扩展点要么接消费者要么移除；settings.yaml 漂移加启动断言 |
