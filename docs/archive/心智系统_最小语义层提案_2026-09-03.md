# 心智系统「最小语义层」提案（2026-09-03）

> 状态：**提案（设计稿）**，仅评估设计，未实施任何改动。
> 目的：修复心智系统本次暴露的核心逻辑缺陷 —— **没有“概念 → 权威源 → 关系”的语义层**，导致「待办」这类高频意图只能靠 agent 临场猜。
> 总原则：**薄契约 + 开放正文**。只对“系统要据此路由/查询/状态流转”的少数字段做结构化；正文、备注、原因、细节一律自由文本。

---

## 1. 要解决的问题（为什么做）

这次“还有啥待办项”出错，根子不在“我没读到文件”，而是心智系统里**没有一个地方定义**：
1. “待办 / 进度 / 建议”分别是什么、边界在哪；
2. 哪个才是**唯一权威源**（问“待办”到底以哪份为准）；
3. 它们之间是什么关系（建议跟待办不是并列两本子，而是**进料 → 筛选 → 成品**的上下游）。

因为没有这层语义，agent 只能靠“文档名/标题 + 目录索引”猜 → 多个文档都“长得像待办”时必猜错。**这就是要补的一层。**

---

## 2. 概念注册表（最小语义层）

> 落点（若批准）：`mind\L1\Concepts.md`（L1 法律层，定义概念契约；正文仍自由）。
> 约定：每个概念 = 【定义】+【唯一权威源】+【与其他概念关系】+【机器可读薄字段】。

### 2.1 待办 `todo`

| 项 | 内容 |
|---|---|
| **定义** | 当前 / 后续要做的**可执行事项**（“现在该做什么”的答案）。 |
| **唯一权威源** | `mind-private\Project\DSHOME\project.md`「下一步（待办）」区；经 `/api/mind/todos` 读写。 |
| **关系** | 由「建议（采纳）」promote 而成（`promotedFrom` 指回建议）；是「进度/状态」的结果来源。 |
| **薄字段（机器可读）** | `status` = `pending`/`done`/`deferred`/`waiting`（开放可扩展）<br>`priority` = `P0`/`P1`/`P2`（可扩展）<br>`source` = `project-board`/`audit-suggestion`/`session`/`self-check`<br>`promotedFrom` = `<建议id>` 或 `null` |
| **正文** | 自由文本，不结构化；仅上面 4 个字段结构化。 |

### 2.2 进度 / 状态 `progress`

| 项 | 内容 |
|---|---|
| **定义** | 项目 / 系统当前的完成度与已有结果（“做到哪了”）。 |
| **唯一权威源** | `project.md`「进度状态」区。 |
| **关系** | 是「待办」「建议」处置后的结果汇总。 |
| **薄字段** | 最少 `updatedAt`（可选）；主体保持 prose 表，不设死枚举。 |
| **正文** | 自由文本 / 表格为主。 |

### 2.3 建议 / 评估产出 `suggestion`

| 项 | 内容 |
|---|---|
| **定义** | 评估 / 审计 / 巡检发现的“可以考虑改”的**候选点**，不一定执行。 |
| **唯一权威源** | 评估 / 审计 / 巡检产出（如 `DSHOME项目评价报告_*.md`、机制体检输出、自清理巡检发现）；**候选池 = 待筛选**。 |
| **关系** | `suggestion` --采纳--> `todo`（被采纳转成待办）；`rejected`/`deferred` 留在建议。 |
| **薄字段（机器可读）** | `status` = `candidate`/`accepted`/`rejected`/`deferred`<br>`priority` = `P0`/`P1`/`P2`<br>`promotedTo` = `<待办id>` 或 `null`<br>`source` = `<报告/巡检>` |
| **正文** | 自由文本。 |

### 2.4 （补充，非本次重点）记忆 / 技能

| 概念 | 权威源 | 走哪个 |
|---|---|---|
| 记忆 / 教训 / 偏好 | `mind-private\L3\index\`（+ `_index`） | `/api/mind/search` + `dup-check` |
| 技能 / 怎么做 | `mind\L2\Skill\`（+ `_index`） | `_index` + 文件 |

## 3. 路由规则（意图 → 概念 → 唯一权威源）

| 用户问 | 概念 | 走哪个 |
|---|---|---|
| 待办 / 下一步 / 该做什么 | `todo` | **`/api/mind/todos`**（唯一事实源 = `project.md` 下一步） |
| 进度 / 做到哪了 / 状态 | `progress` | `project.md`「进度状态」 |
| 评估 / 审计 / 有什么可改 | `suggestion` | 评估 / 审计 / 巡检产出（**明确标为“建议 ≠ 待办”**） |
| 记忆 / 教训 / 偏好 | `memory` | `/api/mind/search` + `dup-check` |
| 技能 / 怎么实现 | `skill` | `mind\L2\Skill\_index` + 文件 |
| 本轮执行清单 | — | `dsh-tool-todo`（todo_write/todo_read） |

> 路由表本身就是 L1 契约的一部分；agent 按它走，**不靠背路径、不靠猜**。

---

## 4. 建议 → 待办管线（显式关系，治“建议≠待办”误解）

```
建议（评估/审计/巡检产出）── status=candidate
        │
        ▼  筛选（硬标准：P0/阻塞/明确门禁；或用户拍板）
   采纳（accepted）                             不采纳（rejected/deferred）
        │
        ▼                                        │
  生成/追加一条待办 ─── 写入 project.md 下一步        留在建议，不进待办板
  带 source=audit-suggestion + promotedFrom=<建议id>
        │
   建议.status=accepted, promotedTo=<待办id>
```

- 这样**待办板 = “已筛选后”的执行清单**；**建议 = “进料”**；二者是**上下游**，不再是并列的两本子。
- 新增来源不重写文档：只在建议候选池里加一条类型化记录，被采纳就自动关联到待办。

---

## 5. 防僵死：薄契约 + 开放正文

- **只结构化**“系统要用来判断/查询/流转”的少数字段（如上 `status`/`priority`/`source`/关联 id）。
- **正文 + 备注 + 原因 + 截止 + 草稿**一律自由，不格式化。
- **不设死枚举**：`status`/`priority` 是开放标签，允许新词；不认识的字段按“其他”保留，不报错、不卡死。
- **知识/记忆仍是 prose + frontmatter**，不做全文 schema。

---

## 6. 为什么能治根（对照本次缺陷）

| 本次缺陷 | 本提案怎么治 |
|---|---|
| ① 没有“概念→权威源→关系”层 → 路由靠猜 | 加概念注册表 + 路由表，agent 按表走，不猜 |
| ② “建议≠待办”被一刀切 | 建议→待办是显式**管线**，不是互斥 |
| ③ `AGENTS/Tree/Power` 索引漂移（`00_约定` 等） | 路由/指针统一引用 `/api/mind/todos` + `Concepts.md`，不再硬编码多条易漂移路径 |
| ④ 自进化“靠记录/规则、闭环弱” | 为后续“偏好作为活信号”在同层留了落点（`memory`/`preference` 概念），可作软输入 |

---

## 7. 本次不做什么（边界，防蔓延）

- **不改** `dshome-mind` 的运行读取逻辑：`/api/mind/todos` 暂仍可用“解析 `- [ ]`”方式，**不阻塞**。二期再把 `readTodos`/`mutateTodos` 升级为“读 `status/priority/source` 薄字段”。
- 不全文 schema 化、不引入数据库 / 死枚举；仍是**纯文件 + frontmatter/字段**。
- 不新增“谁拍板”的人工开关 —— 筛选走**硬标准，或用户明确拍板**，不是我每次停下来问。
