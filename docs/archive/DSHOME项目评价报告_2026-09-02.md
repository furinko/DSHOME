## 3. 亮点（有据可查）

1. **心智体系纯文件化重构（09-02），是可交接的架构级升级**：`dsh-evolve` 退役 → `mind\`（L0 宪法/L1 法律/L2 能力/L3 记忆 + Project + TRASH）**双区体制**（出厂固件入库 / 本机实例 `mind-private\` gitignore）、`dshome-mind` 插件提供 `/api/mind/{status,read,graph}` + `conversation.view`「心智」SVG 分层图谱；`docs/ARCHITECTURE.md` 把这套决策（含"为什么弃 dsh-evolve"）和**新债**都如实记录——不自欺、接手友好。
2. **事故复盘文化延续得最扎实的一次**：ISSUE-004（装 `dsh-input-traffic` 后界面起不来）没停留在"装插件导致的"，而是排查出**双根因**——L4 `cordis.patch.yml` 被清成纯注释（boot 层硬校验启动即崩）**才是主因**，装插件只是触发了重启；并连带 `pnpm-lock.yaml` 的 `settings.autoInstallPeers: true→false` 副因。最终沉淀：L4 清空须留显式 `[]`、装插件前做回滚三件套、改配置/装插件后必须重启验证。这种"推翻直觉 → 根因定位 → 门禁沉淀"的闭环在个人项目里极为难得。
3. **架构文档可交接、自曝其短**：`docs/ARCHITECTURE.md`（09-02）完整记录 6 包、心智双区、rationale 与 §9 新债；`docs/README.md` 分类导航仍在。唯一注意点：README 的**「四包」表仍只列 4 包**、与结构树的 6 包不一致（详见 §4.4），虽未清干净，但整体文档质量仍优于绝大多数个人项目。
4. **零依赖工程细节**：启动器/卸载器用 Windows 自带 csc 编译（`build-launchers.cmd`，`DSHOME.exe`/`UninstallDSHOME.exe` 极小）；junction 运维纪律（删 junction 用 `Remove-Item` 勿用 `rmdir /s /q`）；依赖版本全锁定 + 全量 bump 策略延续。
5. **版本一致性意识**：v0.3.0 在 `packages/dshome/package.json`、`dshome-theme` 品牌 `DSHOME_VERSION`、根 `updates.json` 三处一致（虽然发布清单仍有漏网，见 §4.1）。

## 4. 扣分点与发现的问题

### 4.1 🔴 `updates.json` 清单漂移仍然存在（实测确认）

| 位置 | 内容 | 结论 |
|---|---|---|
| 根 `E:\DSHOME\updates.json` | version `0.3.0`，sha `d7fede0e7fa9c4aeeb18087f6c85798d27caf8472ff90711c349aa6d9d0fd645` | 已同步到 v0.3.0 |
| `E:\DSHOME\build-stage\payload\updates.json` | sha `a826ed34a35936b37565f5ef2bee03105c9b07a001282b082ed3fafeb0a9541d` | ❌ **仍为旧值**（上期被定义为 `a826ed34…` 旧值，非 v0.2.0 发布 sha `54d2c586…`） |

影响：`updater.cjs` 固定从 GitHub raw 拉取**仓库根** `updates.json`；根已正确指向 v0.3.0，但 `build-stage\payload\updates.json` 这份"打进安装包"的清单**仍停留在旧值**——若 0.3.0 发布物尚未重建（则清单未同步），或已重建（则两份清单未对齐），都属于**发布清单未闭环**。此外线上 v0.3.0 安装包的真实 sha **未在本机核对**（需网络比对 GitHub release）。

### 4.2 无自动化测试 / 无 CI

- `packages\` 下仍无任何 `describe(` / `it(` 单元测试（仅正则 `.test()` 误命中）；
- 根仓库无 `.github/workflows`，无持续集成；
- 打包依赖本机 ISCC（曾出现"本机未找到 ISCC"导致重建延迟）；
- 4 次事故（ISSUE-001/002/003/004）全部靠人工踩出/人工排查，缺少自动化回归防线。

### 4.3 🔴 L4 覆盖层"空化"脆点（ISSUE-004 揭示）

`profiles/dshome/cordis.patch.yml`（L4 本机覆盖位）语义上应是"补丁数组"，但被 `dsh-app-boot` 硬校验为**顶层 YAML 数组**；当它被清成纯注释时解析为 `null` → **任何新启动即崩**（`parsePatchList` 抛 `must be a top-level YAML array of loader patch entries`）。这不是装插件导致的，而是**覆盖位被清空时没有保留显式 `[]`**。当前虽已修复并沉淀"清空须留 `[]`"，但它暴露了**boot 层无自动兜底**、以及**"HTTP 200 冒烟"无法探测配置层空化**的盲区。

### 4.4 其他小项

- **ISSUE-004 复盘文未收录入库**：完整复盘在 `DSHOME-ISSUE-20260901-PLUGIN-INSTALL-CRASH.md`（工作区），仓库 `docs/incidents/` 仍只到 ISSUE-003；
- **README 内部仍漂移**：结构树列 6 包，但「四包」表仍只 4 包（缺 `dshome-assistant-identity`、`dshome-mind`）——上期"四包表漏 `dshome-assistant-identity`"未真正清干净，且 README 自身（树 vs 表）口径不一；
- **根 `package.json` 的 `verify` 未串 `verify-payload`**：`verify` = `pnpm build && pnpm smoke`，打包门禁 `verify-payload.mjs` 有脚本但未进默认门禁链（仍靠人工"出包前必跑"）；
- 已知设计债未排期（见 `docs/ARCHITECTURE.md` §9）：`dshome/core` 扩展点零消费者；settings.yaml 管理视图与 patch 加载真相可能漂移；纯文件心智**无自动召回/注入**（靠 Tree 索引 + 上工强制加载 + grep）；心智图谱**边稀疏**（related 需随沉淀持续补充）；面板为会话作用域。
